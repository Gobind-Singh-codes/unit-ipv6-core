The DUT errors instead of processing. Pointers are quoted from the deviations:

- `T4C2 ptr=50` ×1 — IP-01-002 (DestOpt with PadN **only**; our TX bytes

Pattern: anything containing Destination Options or Routing headers is rejected;
repetition is rejected; some two-header orders containing Fragment are rejected.

### 1.4 NOT_APPLICABLE (2)

IP-01-005 / IP-01-006 (AH / ESP singletons): no IPsec security context exists,
so the condition cannot be constructed. Correctly not fabricated.

### 1.5 DUT reading (observation, not a verdict on intent)

The DUT processes HBH, Fragment, and H→F, and correctly discards action-`01`
options — but rejects all Destination Options (even PadN-only), all Routing
headers (even SegLeft-0-ignore cases), repeated headers, and never emits
Parameter Problem for unknown options. This is the signature of **firewall-style
extension-header hardening**, not a broken stack. Whether that policy is
acceptable for this DUT's role is an operator decision; the FAILs are the
accurate conformance record either way.

## 2. Gaps — what still needs to be done

### 2.1 Coverage gap: multicast-destination variants (IP-02, IP-04)

- **IP-02** (action `11`) requires the error *only if the destination was not
  multicast. The suite proves the unicast half (FAIL: no error sent) but never
  sends the multicast half (which must be discarded *without* an error).
- **IP-04** (action `10`) requires the error *regardless* of multicast. Only the
  unicast half is exercised; the multicast-destination case is untested.
- Action: add `--mcast-dst`-driven negative cases (multicast L2 mapping already
  exists in `common/packets.py:eth_dst_for_ipv6`) withTx-on-wire + control
  reasoning; expect IP-02-mcast → PASS-if-silent, IP-04-mcast → FAIL-if-silent.

### 2.2 Coverage gap: IPv6 base-header fields

`PROJECT.md §14` lists base-header fields, payload length, Hop Limit, Traffic
Class, and Flow Label. The current IP-01 matrix covers extension-header
ordering/repetition only; malformed/truncated headers, invalid payload-length,
and header-field edge cases have no tests yet. These are new test IDs (not ER
expansions — label them `RFC-CONTEXT` per `ER-REFERENCE.md` scope rules, since
Table-3 contains only IP-01…IP-05).

### 2.3 Coverage gap: exhaustive and security profiles never run live

The evidence (`IP-01-matrix.json`, 46 entries) is the **core** profile. Not yet executed:

- 120 ordered triples (`IP-01-400…519` generator exists, only 8 sampled),
- 4/5/6-header permutations (360/720/720, `matrix_long`, bounded by
  `IP01_MAX_CHAIN_LENGTH`),
- security profile (AH/ESP chains need a real IPsec context; currently
  NOT_APPLICABLE by design).

The ER phrase "any order and any number" is therefore sampled, not exhausted —
correctly recorded, but a longer maintenance-window run of `--profile exhaustive`
is still outstanding.

### 2.4 Interpretation gap: the DUT's odd pointers

`ptr=50` on a PadN-only option and `ptr=6` flagging a Next Header the DUT
accepts elsewhere suggest the DUT parses (or reports) differently from a
reference stack. Worth a vendor query and, per the annexure rule, Helpdesk
confirmation where implementation context differs from the ER's RFC. The raw
material is preserved (`pcap/IP-01-002.pcap`, `pcap/IP-01-116.pcap`).

### 2.5 Method debt (small, 8200-scoped)

- Silence-FAILs rest on `auto` delivery proof (TX + liveness). A `--delivery-proof
  strict` re-run is the available conservative cross-check; keep both runs if the
  result is disputed.
- `dut_packets` ledger is capped at 10 summaries per test — enough for this run
  (max observed: 1–2 DUT packets), revisit if a noisier network is used.
- BPF is now test-traffic-only; re-verify `tx_seen` stays `true` on a quieter
  lab (it was validated on this noisy one, so risk is low).
